# 链重组（reorg）规则

## 1. 规范链选择

在所有 `connected=1`（能追溯到创世块）的区块里选链头（tip）：

1. **累计工作量 chainwork 最大者胜**（"最重链"，而非简单数块数）；
2. chainwork 相同（等长且等工作量）时，取 **tip 哈希字典序更小** 的链。

第二条是确定性平局规则：最终规范链只取决于数据本身，与投放先后顺序无关。
`chainwork` 可在投放 JSON 里显式给出；缺省按每块 +1（即高度 +1）。

## 2. 到达处理（支持乱序）

- 父块未知 → 缓存为孤儿（`connected=0`），不拒绝、不上规范链、查询不可见。
- 父块已存但高度不等于本块高度 - 1 → 拒绝（`parent_chain_error`）。
- 父块已连通 → 把该块标记 connected，并向下级联其所有已缓存的后代。

## 3. 何时触发重组

每次写入后重选最重 tip；当 tip 与当前规范链头不同时，在**同一个数据库事务**中：

1. 从新 tip 沿父指针回溯到创世（遇到环拒绝，见上）；
2. 清空 `canonical` 表；
3. 把新链逐高度写入 `canonical`；
4. 提交。

因此重组是原子的：要么查询看到旧链，要么看到完整新链，
不会出现"区块换了但交易索引还是旧的"这种半更新状态。

## 4. 回滚的语义

- 被替换链上的区块仍在 `blocks` 表里（保留分叉历史），但退出 `canonical`；
- 这些区块的交易记录仍在 `transactions` 表，但所有查询都 `JOIN canonical`，
  所以按高度、按交易哈希、按地址都查不到已回滚交易——**逻辑上干净回滚**；
- 若之后旧链延长、chainwork 反超，会再次重组回来，其交易自动恢复可见；
- 若交易哈希在两条链上同时出现且指向不同区块，第二次投放直接 `duplicate_tx` 拒绝，
  保证一笔交易全局唯一，不会在链间"串味"。

## 5. 链头不倒退

- 一个已连通区块的 chainwork 固定不变；新到达的低高度块不可能成为更重的 tip，
  所以链头高度/身份不会因为迟到块而后退。
- 孤儿块在父块到达前完全不影响链头。

## 6. 并发可见性

- 写路径在进程内加锁，并使用 `BEGIN IMMEDIATE` 单事务提交；
- WAL 模式下，查询连接看到的是最近一次已提交快照（read snapshot），
  重组进行中的中间状态对外不可见（见 `tests/test_concurrency.py`）。
