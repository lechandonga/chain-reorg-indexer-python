# 链重组规则

## 1. 链的合法性

一条候选链是从某个区块沿 `parent_hash` 回溯得到的块序列，合法当且仅当：

1. 能回溯到创世块（`height=0, parent_hash=0x0`）；
2. 高度严格连续：`0,1,2,...`，且每块的 `parent_hash` 等于前一块 `hash`；
3. 不形成环。

父块尚未归档的区块处于**暂存态**，不能成为链头或延伸链——这保证了乱序投放时
「链头绝不倒退」：在补齐父块之前，当前链头保持不变。

## 2. 最长链与等长规则

每次有新区块归档后：

1. 收集以它为根的归档子树中所有**叶子**（没有孩子的块）作为候选 tip（同时保留当前 tip）；
2. 对每个候选 tip 回溯到创世，取长度最大的链；
3. 长度相同：**不重组**——若其中一条是当前链，保留当前 tip；
   若当前为空（首条链），按 tip 哈希字典序取最小。

等长不抖动 + 字典序兜底，保证了多次运行、不同投放顺序下结果唯一确定。

## 3. 分叉点与回滚区间

对比当前链与目标链：

- 从创世开始最后一个 hash 相同的高度记为 `fork_height`；
- 需要清空旧链的起始高度为 `fork_height + 1`（创世就分叉则从 0 开始）；
- 新尾 = 目标链在分叉点之后的块序列（高度递增）。

```
旧链: G - A1 - A2 - A3
新链: G - B1 - B2 - B3 - B4
            ^fork_height=0，回滚 >=1，插入 B1..B4
```

## 4. 原子换链（无半更新）

整个切换在单个 SQLite 事务（`BEGIN IMMEDIATE`）内执行：

1. **校验新尾**：新尾内部交易哈希唯一；新尾交易不与分叉点之前的共享前缀重复。
   注意不能拿全量索引比较——旧尾交易此刻还在，但它们马上要被删除。
2. **删旧尾**：从 `rollback_height` 起删除 `canonical`、`transactions`、`tx_addresses`。
3. **插新尾**：逐块写 `canonical` 与交易/地址索引。

任一步失败 → `ROLLBACK`，链头和所有索引完全停留在重组前（见
`tests/test_reorg.py::test_reorg_is_atomic_no_half_state`）。

## 5. 暂存块补连通

区块首次到达时：

- 若父块已知且高度自洽：归档并触发链重算；
- 若父块未知：只归档为暂存块，返回 `accepted_pending`；之后任意祖先块到达时，
  会沿 `blocks.parent_hash` 找到这次暂存的后代并参与最长链竞争。

这就是「倒序投放 3,2,1,0，创世一到链头直接到高度3」的实现方式。

## 6. 并发与查询一致性

- 所有读写共用一把可重入锁；写事务全程持锁，读者在同一把锁下获得快照。
- 查询只走 `canonical` JOIN `blocks` 与 `transactions`，故：
  - 不会返回回滚掉的区块/交易；
  - 边写边查看到的永远是一条完整链（见 `tests/test_concurrency.py`）。
